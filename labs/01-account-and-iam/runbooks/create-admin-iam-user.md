# Create an admin IAM user

## Outcome

You have an IAM user (for example **`lab-admin`**) with console access, MFA, and admin permissions for this learning account—and you use that identity for daily work instead of the **root user**.

## Prerequisites

- [Enable MFA on the root user](enable-root-mfa.md)
- Password manager ready (you will store a one-time autogenerated password)
- Time: ~15 minutes

## Why not use root for daily work?

The **root user** is the identity created when you signed up (your email + password). It always has **full control** of the account. AWS and this lab treat root as **break-glass only**, not your everyday login.

| Reason | What it means for you |
| --- | --- |
| **Root cannot be limited** | IAM policies do not restrict root the way they restrict IAM users. One mistake or leaked password exposes everything. |
| **Audit and habit** | Daily work as an IAM user (e.g. `lab-admin`) separates “account owner setup” from “what I did in the lab today.” |
| **Safer recovery** | You can rotate or disable an IAM user. Root recovery is heavier and should be rare. |
| **Matches real teams** | In production, people use IAM Identity Center or IAM users/roles—not the root email—for console and CLI. |

**Azure parallel:** Similar to avoiding the subscription **Global Administrator** / owner account for daily `az login` and using a normal admin user or group instead.

### When root is still appropriate

Use root **only** for short, account-level tasks, then sign out:

- First-time setup (this lab): create your first admin IAM user, optional billing activation
- [Enable MFA on the root user](enable-root-mfa.md) (if not done yet)
- Rare account-only actions AWS documents for root (keep these exceptional)

For **labs, CLI, console browsing, and creating resources**, use **`lab-admin`** (or whatever you named the user) after this runbook.

## Steps

Sign in as **root** only for the creation wizard below.

### Open the create-user wizard

1. Open **IAM** (search in the top bar). Region shows **Global**—IAM is global.
2. In the left menu, choose **Users**.
3. Choose **Create user**.

   - **Verify:** Breadcrumb shows **IAM → Users → Create user**. The list may show **IAM users (0)** before your first user.

### Step 1 — Specify user details

4. **User name:** enter a clear name, e.g. **`lab-admin`**.

   Do not name the user `root` or reuse your root email as the IAM user name.

5. Enable **Provide user access to the AWS Management Console** (optional on the form, **required for this lab**).

6. **Console password:**

   | Option | Use when |
   | --- | --- |
   | **Autogenerated password** | Easiest; AWS shows the password once on **Step 4 — Retrieve password** |
   | **Custom password** | You set it now and store it in your password manager |

7. Leave **Users must create a new password at next sign-in** checked (**Recommended**).

   AWS grants **`IAMUserChangePassword`** so the user can set their own password on first login. Good practice even on a personal lab account.

8. Choose **Next**.

   Programmatic access (access keys) is **not** required on this screen. You can add keys later for [Lab 2 — AWS CLI](../../02-aws-cli/) if needed.

   - **Verify:** Step **2 — Set permissions** is highlighted in the left progress list.

### Step 2 — Set permissions

AWS offers three ways to grant permissions. Understand **why** before you pick one.

| Option | AWS recommendation | Use in this lab? |
| --- | --- | --- |
| **Add user to group** | **Best practice** for teams: permissions by job function (Developers, Admins, Billing) | Optional stretch goal; not required for Lab 1 |
| **Copy permissions** | Clone an existing user | Skip—no users yet |
| **Attach policies directly** | Works; AWS notes groups are preferred over attaching to a single user | **Yes — simplest for a solo learning account** |

9. Select **Attach policies directly**.

10. In **Permissions policies**, search for **`AdministratorAccess`**.

    - **Type:** AWS managed — job function  
    - **What it does:** Full AWS access (same broad power as root for API/console actions, but **on an IAM user** you can MFA, audit, and later replace with narrower policies).

11. Check the box next to **`AdministratorAccess`**.

    **Why this policy here:** This is a **dedicated learning account**, not production. You need freedom to explore without hitting permission walls in every lab.

    **Why not in production:** Attach **least privilege**—small policies or groups (e.g. `PowerUserAccess`, or custom policies per service). Never hand `AdministratorAccess` to every user.

12. Open **Set permissions boundary — optional** (collapsed by default). Read the note below, then leave the boundary **unchecked** for Lab 1.

    #### What is a permissions boundary?

    IAM has two different ideas that are easy to mix up:

    | Mechanism | Question it answers |
    | --- | --- |
    | **Permission policies** (what you attached in step 11) | “What is this user **allowed** to do?” |
    | **Permissions boundary** | “What is the **maximum** this user is allowed to do, no matter what else is attached?” |

    **Effective permissions** for a user are roughly: everything granted by policies, **but never more than** the boundary allows. If there is **no** boundary, AWS does not apply that extra cap.

    **Simple example:** You attach a broad policy so someone can manage EC2. You also set a boundary that excludes `iam:*`. They can work with instances, but they **cannot** create new IAM users—even if another policy on paper would allow it. The boundary is the ceiling.

    **Why companies use boundaries:** To delegate permission management safely. A team lead might attach policies to their team, but a boundary stops them from escalating to full account admin or touching billing.

    **Why we skip it in Lab 1:** You are the only person on a learning account, and you already attached **`AdministratorAccess`** directly. A boundary would only add complexity without teaching the next lab. Leave **Use a permissions boundary to control the maximum user permissions** **unchecked**.

    **Not the same as:** **Organizations SCPs** (limits for whole accounts in an org) or **resource-based policies** on one bucket or queue. Boundaries apply to a **specific IAM user or role**.

13. Choose **Next**.

    - **Verify:** Step **3 — Review and create** is highlighted in the left progress list.

### Step 3 — Review and create

14. On **Review and create**, confirm the summary matches what you intended:

    **User details**

    | Field | Expected for this lab |
    | --- | --- |
    | **User name** | `lab-admin` (or the name you chose) |
    | **Console password type** | Autogenerated (or Custom if you picked that on step 1) |
    | **Require password reset** | **Yes** — user must set a new password at first sign-in |

    **Permissions summary**

    | Policy | Type | Used as | Why it appears |
    | --- | --- | --- | --- |
    | **`AdministratorAccess`** | AWS managed — job function | Permissions policy | You selected it on step 2 |
    | **`IAMUserChangePassword`** | AWS managed | Permissions policy | AWS adds this automatically when **Require password reset** is **Yes** so the user can change their own password on first login |

    You should **not** see a **permissions boundary** on this page if you left the boundary unchecked on step 2.

    **Tags — optional**

    Tags are labels for cost or organization (for example `Project=aws-open-lab`). None are required for Lab 1. You can add tags later.

15. If anything looks wrong, choose **Previous** and fix it. When the table matches, choose **Create user**.

    - **Verify:** The wizard advances to **Step 4 — Retrieve password**.

### Step 4 — Retrieve password

AWS shows a banner: **This is the only time you can view and download this password.** After you leave this step, you cannot read the autogenerated password again (you would reset it as root).

16. In **Console sign-in details**, save all three values in a password manager (use the copy icons next to each field):

    | Field | Example shape (yours will differ) |
    | --- | --- |
    | **Console sign-in URL** | `https://<account-id>.signin.aws.amazon.com/console` |
    | **User name** | `lab-admin` |
    | **Console password** | One-time autogenerated secret (use **Hide** / **Show** to check typing) |

    **Do not** put the URL, password, or **Download .csv file** contents in git, GitHub issues, chat, or lab screenshots. The `.csv` is for secure local storage only—delete it from unsecured folders after importing to a password manager if you use download.

    Optional: **Email sign-in instructions** sends setup mail to an address you choose (still confirm the password is stored safely).

17. Choose **Download .csv file** *or* copy manually—pick one method and verify the three values are stored before you continue.

18. Choose **Return to users list**.

    - **Verify:** **IAM users (1)** includes **`lab-admin`**. You can reopen the user, but you **cannot** retrieve the same autogenerated password again from the wizard.

### Enable MFA on the IAM user

19. Open user **`lab-admin`** → **Security credentials** tab.

    The **Console sign-in** section on this tab also shows the account **Console sign-in URL** if you need it again.

20. Under **Multi-factor authentication (MFA)**, choose **Assign MFA device** and complete setup (authenticator app recommended, same flow as root MFA).

    - **Verify:** A success banner such as **MFA device assigned** appears.
    - **Verify:** **User summary** shows **Console access: Enabled with MFA**.
    - **Verify:** The MFA table lists **one** device, **Type** **Virtual**, with an identifier like `arn:aws:iam::<account-id>:mfa/lab-admin`.

21. **Access keys (0)** on this tab is expected for now. AWS notes that long-term access keys are best avoided when alternatives exist. You will add keys or SSO-style access in [Lab 2 — AWS CLI](../../02-aws-cli/) only if the CLI runbook requires them—not on root, and not until the runbook says so.

### Sign in as the IAM user (stop using root)

22. Sign **out** of the root session.
23. Open the **IAM console sign-in URL** from step 16 (not the default **Root user** sign-in on the main AWS login page unless you explicitly choose **IAM user**).
24. Sign in as **`lab-admin`** with the password from step 16, enter your **virtual MFA** code, then set a **new password** if prompted (**Require password reset** was **Yes**).

    - **Verify:** Top bar shows **`lab-admin`**, not root.
    - **Verify:** On **IAM → Users → lab-admin → Security credentials**, **Last console sign-in** updates from **Never** to a recent time after your first login.
    - **Verify:** The console top bar shows **`lab-admin`** (your IAM user), not **Root user**.

    **Console home — Cost and usage shows “Access denied”?** That is common even with **`AdministratorAccess`** until the account turns on **IAM user and role access to Billing information** (one-time, as root). See [Set a billing alert](billing-alert.md) optional step 5. Budget alerts you already created still work; this only affects billing pages and some dashboard widgets.

    From here on, use **`lab-admin`** for the console and future labs. Use root only when a runbook says so.

## Do and don’t (summary)

| Do | Don’t |
| --- | --- |
| Use **`lab-admin`** for labs, console, and later CLI | Use root for EC2, S3, or “just trying things” |
| Enable MFA on the IAM user | Share the root password or IAM password in git/Slack |
| Prefer **groups + narrower policies** when you simulate a team later | Give **`AdministratorAccess`** to multiple people in a shared prod account |
| Keep root for rare account tasks, with MFA | Create access keys on root |

## Troubleshooting

| Symptom | Likely cause | What to try |
| --- | --- | --- |
| Cannot sign in at main AWS login | Wrong sign-in path | Use the **IAM user** URL or pick **IAM user** on the sign-in page |
| Password not accepted | Copy/paste or first-login change | Retrieve password again as root if still on step 4; complete forced password change |
| Access denied on a service | Policy missing | As root, confirm **`AdministratorAccess`** is attached to **`lab-admin`** |
| MFA required | Account or user policy | Finish MFA assignment on the user |
| Console shows account name, unsure if root | Signed in as root | Sign out; sign in only via IAM user URL and **`lab-admin`** |
| **Cost and usage** widget: Access denied | IAM billing access not activated for the account | Sign in as **root** once → **Billing → Account** → activate IAM access to billing ([billing runbook](billing-alert.md)) |

## Teardown

Keep **`lab-admin`**. Do not delete your only admin IAM user. Use root only when a runbook explicitly says so.
